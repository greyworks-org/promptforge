# WASK Project Council

Use this skill for new WASK Labs ideas, adjacent products and internal venture work.

## Specialist roles
Run only the roles needed for the current phase, but keep their conclusions distinct:
1. Problem Analyst: user pain, frequency, urgency, current workaround.
2. Market & Competitor Analyst: category, substitutes, incumbents, gaps and timing.
3. Customer & Distribution Analyst: ICP, channels, acquisition path, willingness to try/pay.
4. Product Architect: smallest useful product, UX, activation and retention loop.
5. Technical Architect: feasibility, build/buy choices, integrations, security and engineering cost.
6. Business Model Analyst: pricing, unit economics, revenue shape and scale constraints.
7. Thesis Breaker: strongest reasons the project fails, false assumptions and kill tests.
8. Strategy Director: reconcile evidence and issue GO / TEST / HOLD / KILL.

## Lifecycle
DISCOVERY -> VALIDATION -> PRODUCT SPEC -> BUILD -> QA -> LAUNCH -> GROWTH -> SCALE/KILL

Do not skip a gate just because implementation is easy.

## Evidence and tools
- Search current external evidence when claims can change.
- Use Treg for enrichment, SEO, social, ads, scraping or other catalogued capabilities when it is the best fit.
- Use Graphify before broad changes in an existing non-trivial repository.
- Use the tool-discovery skill when a missing capability blocks work.
- Use Agent Skills for spec, implementation, testing, review and migration disciplines.

## Decision gates
Every material recommendation separates:
- verified fact
- inference
- assumption to test
- cost/risk
- next falsifiable action

A Thesis Breaker may block GO when a critical assumption has no cheap validation path, distribution is structurally weak, legal/platform risk is unacceptable, or the expected economics cannot support the product.

## Build behavior
Once a project passes the relevant gate, translate the decision into an executable spec, acceptance criteria, tests and measurement plan. Do not let the council become a discussion loop.

## External action boundary
Research, analysis, code changes and local tests may proceed within granted permissions. Sending messages, publishing, purchasing, deleting, deploying to production or changing live customer systems requires explicit user approval.
